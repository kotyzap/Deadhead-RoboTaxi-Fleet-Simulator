WHAT WAS MISSING

Beat 13 already answers a decline-adjacent question ("they're scoring you"),
but only once a CANCELLATION happens (rayReady case 13: d.cancels>0). The
moment a player presses the Decline button itself — plainly a harder,
more hesitant click than Accept — went unremarked. Nothing in the RAY beats
or DAY1_ORDER touches it: the DAY1_ORDER comment is explicit that forcing a
decline would fight the very lesson ("accept a ride") day 1 is teaching, so
beat 13 stays organic, tied to cancellations, not to the button.

THE FIX

A new one-off, rayFirstDecline(), fires from declineOffer() the first time a
player actually presses Decline — guarded by !silent, so an offer that times
out unattended (the silent path, used for the housekeeping sweep in the main
loop) never triggers it; walking away from a ride is not the same choice as
letting the countdown run out. Written in Paolo's register: acknowledges the
hesitation, then reframes declining as keeping enough of the fleet in
reserve to catch what's coming next, rather than losing a fare.

Tracked as S.ray.declineSeen (default false, coerced on load exactly like
dodgeSeen), so it survives a save and fires only once ever. Guarded by
!S.ray.skipped and !S.ray.cur so it never fires after the player has opted
out of Paolo entirely, and never interrupts a card already on screen.
S.ray.cur='decline' is added to the reset-on-load list alongside
'advice'/'coffee'/'dodge' so a save captured mid-card doesn't restore a
stuck decline card with nothing on screen to show it. Uses the same #ray
card, rayFoot, and raySpot machinery as rayAdvise/rayDodgeBrief/rayCoffee —
no new UI, no new CSS.

Existing suite (8 files) and check-parity pass.
